# Implementation Plan: Demo mode for a public demonstration

**Branch**: `003-demo-mode` | **Date**: 2026-10-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/003-demo-mode/spec.md`

## Summary

A demo mode, selected with `DEMO_MODE=true` and off by default, turns the server into a self-contained public demonstration that fits Render's free web service (one port, 0.1 CPU, 512 MB, temporary disk, sleep after 15 minutes, 5 GB of outbound bandwidth a month). At start it verifies the published recording against the README's SHA-256, builds the whole session in an in-memory database by feeding every packet through the existing parsers and persistence (measured: 282 ms locally, 2,411 + 2,411 samples, exactly spec 001's ground truth), rewrites the session's and laps' dates to the recording's capture times, seeds the coach cache from a versioned file tied to the recording (checking each entry's insights against today's analysis with a cross-platform tolerance), switches the database to read-only, and only then listens. REST and WebSocket share the platform's `PORT`; the live stream is the existing spec 001 replay loop at `1x`, in-process and broadcast-only, carrying only the player's car, compressed with per-message deflate, to at most 5 connections of at most 5 minutes each, with their own close codes. CORS and the WebSocket handshake accept only the frontend's origin (a browser-only limit); reads are cacheable by revalidation; the coach never calls Anthropic, because demo mode refuses to start with a key. A build configuration compiles to `dist/` and `npm start` runs it. Local mode is unchanged.

With the decisions of the plan review, a full visit costs about 2.2–3.8 MB, so the 5 GB allowance covers **roughly 1,330–2,410 full visits a month**, against about 165–175 at the clarified settings ([research.md](research.md), point 1). The per-IP limit (FR-027) is not adopted, because the platform's client-IP forwarding cannot be confirmed from its documentation.

## Technical Context

**Language/Version**: Node.js ≥ 22.17 (major 22 from `.nvmrc`), TypeScript 5.6.3, `strict`, CommonJS. Unchanged.

**Primary Dependencies**: no new dependency, runtime or development. `ws` 8.18.0 (`noServer` + `upgrade`, `perMessageDeflate`), Express 5.2.1, `cors` 2.8.6, `better-sqlite3`; built-ins `node:http`, `node:crypto` (SHA-256) and the global `fetch` (download).

**Storage**: SQLite through the existing repositories. Local mode: `data/telemetry.db` (or `DB_PATH`), now resolved from the project root. Demo mode: `:memory:`, built at every start, read-only (`PRAGMA query_only = ON`) once seeded. No schema change ([data-model.md](data-model.md)).

**Testing**: `node:test` + `node:assert/strict` via `ts-node/register`, discovered from `src/**/*.test.ts` with no script edit. TDD for the new pure functions, each test seen failing on its own assertion first; one demo integration test against a synthetic recording generated by the test.

**Target Platform**: Linux on Render's free web service for demo mode (build `npm ci && npm run build`, start `npm start`, configured at deploy time); the maintainer's Windows machine for local mode, development and the seed export.

**Project Type**: single backend web service plus CLI tools.

**Performance Goals**: ready within the platform's start window (measured locally: 121 ms decode + 55–72 ms hash + 282 ms build; about ten times that estimated on 0.1 CPU); the live stream at the recording's own 20 Hz; ≤ 10 KiB/s per live connection on the wire (6.7 KiB/s measured, SC-012).

**Constraints**: 512 MB memory (measured peak RSS 171 MiB under ts-node, about 80 MiB of it ts-node's baseline, plus about 256 KiB of zlib state per compressed connection); 0.1 CPU (compression estimated at about 11–12% of the instance per client); 5 GB outbound a month; no paid call except the maintainer's manual seed export; nothing ever written to or read from `data/telemetry.db` by demo mode, the tests or the verification steps.

**Scale/Scope**: one session (the published recording), ≤ 5 simultaneous live connections, about 1,330–2,410 full visits a month within the allowance; no change to analysis, parsing or the coach's prompt.

No `NEEDS CLARIFICATION` remains.

## Design

### Start sequence in demo mode (`src/demo/demoServer.ts`)

1. `parseDemoConfig(process.env)`: `DEMO_MODE`, `PORT`, `DEMO_ALLOWED_ORIGIN`, limits (5 connections, 5 minutes), `DEMO_WS_COMPRESSION` (default `true`), paths; refuse `ANTHROPIC_API_KEY` and `DB_PATH` ([contracts/configuration.md](contracts/configuration.md)). Nothing opened yet.
2. Read the recording, compute its SHA-256, compare with the seed file's `recordingSha256`; in production that value equals `PUBLISHED_RECORDING_SHA256`, which a unit test ties to the README. A missing recording stops the start (T-4).
3. Open the database (`:memory:`), then `buildDemoSession(packets)`: every packet through `dispatchPacket` + `persistTelemetry`, collecting the completed laps' `receivedAt`.
4. `buildCaptureTimes(...)` → `applyCaptureTimes(sessionId, times)`.
5. Validate the seed ([contracts/coach-seed-file.md](contracts/coach-seed-file.md)), including `insightsMatch(entry.insights, buildInsights(pair))` for every entry (research.md, point 7); insert the entries.
6. `PRAGMA query_only = ON`.
7. Create the HTTP server from `createApp({ demo })`; `attachDemoWsServer(server, { allowedOrigin, maxConnections, maxConnectionMs, perMessageDeflate: config.wsCompression ? {} : false, onEvent })`; `listen(PORT, "0.0.0.0")`. `DEMO_WS_COMPRESSION=false` is the way out, without a code deploy, if the summary's process CPU time shows the instance saturated; the start log states whether compression is on.
8. `runReplay(packets, { speed: "1x", loop: true }, { send })`, where `send` dispatches the buffer and broadcasts `toPlayerOnlyMessage(buildWsMessage(...))` for motion, lap data and car telemetry, without persisting. `onPass` logs each pass.
9. Log "pronto" with the elapsed time; start the 15-minute summary (connections, WebSocket and REST socket bytes, coach 503s, process CPU time).
10. `SIGTERM`/`SIGINT`: abort the replay, close the connections with `1001`, close the server and the database.

### Local mode

`server.ts` keeps today's wiring (standalone WebSocket on `WS_PORT` without compression, Express on `HTTP_PORT`, UDP on `UDP_PORT`, per-packet logs), moved into a function and selected when `DEMO_MODE` is unset or empty. `createApp()` with no demo options builds the same Express app as today (`cors({ origin: true })`, the same routers) plus `GET /health`.

### Test strategy (TDD)

For each pure function, the order is: create the module with the final signature and a body that returns a neutral wrong value (never a missing export or a thrown "not implemented"), write the test, run it and **see it fail on its own `assert`**, then implement until green. A test that fails on an import, a type error or a thrown stub does not count as red.

| Pure function | Module | What the tests pin |
|---|---|---|
| `toPlayerOnlyMessage` | `src/demo/playerOnly.ts` | one-element `data` equal to the player's car; `playerCarIndex` 0; other fields untouched; the input not mutated |
| `buildCaptureTimes` | `src/demo/captureTimes.ts` | ISO strings for start, last seen and each lap; throws when a `receivedAt` is missing; last ≥ first |
| `decideOrigin` | `src/demo/liveConnections.ts` | exact match accepted; other origin refused; absent `Origin` accepted; trailing-slash and case variants refused |
| `decideCapacity` | `src/demo/liveConnections.ts` | below the limit accepted; at the limit "full" (4001); the limit configurable |
| `parseDemoConfig` | `src/config/demoEnv.ts` | refuses a non-empty `ANTHROPIC_API_KEY` and `DB_PATH` with the exact messages; requires `PORT` and `DEMO_ALLOWED_ORIGIN`; rejects an origin with a path; defaults 5 connections and 5 minutes; rejects `DEMO_MODE=yes`; `DEMO_WS_COMPRESSION` unset or empty → on, `false` → off, `no` → refused |
| `insightsMatch` | `src/demo/insightsMatch.ts` | equal objects match; 0.35 vs 0.36 matches; 0.35 vs 0.37 does not; a one-ulp difference in a copied distance matches; a corner more or less, a changed boolean or `severity`, `null` vs a number, a missing or extra key do not; the result names the first differing path |
| `validateCoachSeed` | `src/demo/coachSeed.ts` | accepts a valid file; refuses another recording's hash, another session UID, an unknown lap, a duplicate pair, `lapA = lapB`, an unknown `formatVersion`, insights beyond the tolerance |
| `findProjectRoot` | `src/config/projectRoot.ts` | from source, the folder holding this repository's `package.json` |
| README hash | `src/demo/recording.test.ts` | `README.md` contains `PUBLISHED_RECORDING_SHA256`; the committed `demo/coach-seed.json` names it (added once the maintainer has produced the file, so the test is never skipped); a mismatching file is refused |
| Seed export core | `src/demo/exportCoachSeed.ts` | with a fake coach, on a two-lap synthetic recording: one call per pair on an empty seed, zero on a second run, one after one entry is made stale or another model, all again for another recording; a coach failing on the second call leaves one paid pair in the progress, and a run from that partial file makes one call; the progress keeps the previous entries of pairs not yet processed |
| `writeCoachSeedFile` | `src/demo/coachSeed.ts` | writes the JSON to `<file>.tmp` in the same folder and renames it over the file: readable JSON, folder created, no temporary left, an existing file replaced whole |
| `assertExportEnvironment` | `src/demo/coachSeed.ts` | with fake roots (`C:\projeto`, `/projeto`) and an explicit `platform`, so the Windows cases also run on the Linux CI: refuses an unset `DB_PATH`, every spelling of `data/telemetry.db` (resolved from the root; on Windows case-insensitive and with both separators: `./data/…`, `data\…`, a `..` that comes back), and a missing key; accepts `:memory:` and a temporary path |

**What the synthetic tests do not cover.** The export and seed tests run on synthetic recordings of a few samples per lap, so `buildInsights` returns nearly empty insights: they exercise the reuse logic, the fake coach's calls and the validation rules, not the real analysis. The real analysis, and the insight tolerance against it, are exercised only by the maintainer's export on the published recording (tasks.md T061) and by demo mode checking that seed at start (T084). The tool's refusal of `data/telemetry.db` is tested only through `assertExportEnvironment` with a fake root; the spawned test of the tool covers only the refusals that need no real path (no `DB_PATH`; a temporary `DB_PATH` with no key), so no test ever puts the real database's path in an environment.

The request-limit function is not built, because FR-027 is not adopted.

**In-process tests with an isolated database** (`testDb.ts`): `persistTelemetry` returns the completed lap; `applyCaptureTimes` rewrites the rows; after `query_only`, an insert fails; `attachDemoWsServer` (`src/demo/demoWsServer.ts`) on an ephemeral port with `maxConnectionMs` of a few hundred milliseconds closes with 4002, the second connection with a limit of 1 closes with 4001, a foreign origin gets 403, a client that offers per-message deflate gets `permessage-deflate` in `extensions`, and with compression turned off the same client gets no extension.

**Demo integration test** (spawned, like `serverFailFast.test.ts`): a synthetic recording with `receivedAt` and a matching synthetic seed (its insights computed by the test from the same synthetic laps), both written by the test to a temporary folder; the server in demo mode on a free port; asserts one session with the synthetic capture dates, the laps and samples, `Cache-Control` and a `304` on revalidation, the seeded pair cached and another 503, CORS for the allowed origin only, single-car compressed WebSocket messages, and that no file named `telemetry.db` appears anywhere it can see. Plus spawned refusals: the key present, `DB_PATH` present, the recording missing or altered, the seed for another recording, a seed whose insights differ by more than the tolerance; each exits non-zero with its message and binds no port.

**SC-007** is checked twice: automatically, the existing suite (including the replay integration test and the fail-fast tests) stays green with demo mode off; and manually, quickstart.md section C repeats spec 001's measurement with a temporary `DB_PATH`, expecting **2,411 of 2,411** samples per table at `1x`. The in-process ground truth measured in research.md point 3 (2,411 + 2,411) is today's baseline for it.
