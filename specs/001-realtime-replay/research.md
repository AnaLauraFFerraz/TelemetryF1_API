# Research: Real-time replay of telemetry recordings

Each section resolves one open design point from the spec and from the user's planning brief. All are closed — no `NEEDS CLARIFICATION` remains.

## 1. Schema migration for sample deduplication (FR-010)

**Decision**: Add `overall_frame_identifier INTEGER` to `car_telemetry_samples` and `motion_samples`, plus a `UNIQUE` index on `(session_id, overall_frame_identifier)` on each table. Inserts use `INSERT OR IGNORE`. Existing databases are migrated the same way `track_id` already is in `db.ts`: a defensive `ALTER TABLE ... ADD COLUMN` wrapped in try/catch for the expected "duplicate column name" error, run **before** the `CREATE UNIQUE INDEX IF NOT EXISTS` (which would otherwise fail against an old table that doesn't have the column yet). `schema.ts`'s `CREATE TABLE IF NOT EXISTS` is updated so a fresh database gets the column natively; the unique indexes move out of `SCHEMA_SQL` into `db.ts`'s migration block, since they depend on the column existing on *either* path (fresh create or defensive alter).

**Rationale**:
- `overallFrameIdentifier` is the only field in the protocol that is documented in this codebase as never resetting or going backward on a flashback (`src/telemetry/header/types.ts`), which is exactly what session time and lap distance do (the known multi-pass-per-lap limitation this spec explicitly stays out of). It is therefore the only safe natural key for "this is the same packet."
- Verified directly with `better-sqlite3` in this environment: a `UNIQUE` index tolerates unlimited `NULL`s in the indexed column (SQLite's default, standard SQL semantics — `NULL` is never equal to another `NULL`). Existing rows get `overall_frame_identifier = NULL` after the migration and do not collide with each other or with anything else; only two rows that both have the same non-null value collide, which is exactly the intended behaviour.
- `listCarTelemetrySamplesForLap` / `listMotionSamplesForLap` (read by `sessionsRouter` and `analysisRouter`) use explicit column lists, not `SELECT *` — confirmed by reading both repositories. Adding the column therefore has **zero impact on the REST/WS contract**; nothing needs to be flagged to the frontend under Constitution VI.
- `INSERT OR IGNORE` keeps the "record what is known, never invent" principle intact: a duplicate insert is silently dropped (it would have been identical data), never silently *altered*.

**Alternatives considered**:
- Deduplicating by `(session_id, lap_distance, session_time)` — rejected: both regress on a flashback, which is the one case this key most needs to survive.
- A separate `replay_runs` or `packet_log` table to track "seen" frames instead of a `UNIQUE` index — rejected as unnecessary indirection; the index enforces the invariant at the point of insertion, which is simpler and cannot drift out of sync with the data it protects.

## 2. Determinism across a loop boundary (FR-011, and the user's point 2)

**Finding**: decimation itself is *already* empirically deterministic across the loop boundary for the Interlagos recording, because within every captured tick `LapData` (packetId 2) is sent before `Motion`/`CarTelemetry` (confirmed by decoding the first and last 15 packets of the file) — so `lapProgress.lapNumber` always flips to the new pass's lower lap number before any sample-write decision is made for that pass. But this is incidental to this recording's own packet order, not guaranteed by the protocol, and it does **not** help `lapCompletionDetector`, which is broken by design across a loop boundary: its "highest lap number ever seen" guard (`if (newLapNum < previousSnapshot.lapNumber) return null`) never resets within a session, so after pass 1 ends on a high lap number, pass 2's lower lap numbers are permanently ignored — no lap is ever upserted again. This directly violates FR-011 ("a lap reported in pass 2 MUST overwrite the equivalent lap from pass 1"), independent of packet order luck.

**Decision**: `sessionContext.ts` tracks the highest `overallFrameIdentifier` seen per active session. At the top of `getActiveSession` (called by every `handle*Packet` function, so this fires once per relevant packet regardless of type), if the current packet's `overallFrameIdentifier` is **more than `PASS_RESTART_THRESHOLD_FRAMES` (100) below** the highest seen so far, the session is treated as having restarted a pass: a fresh `lapCompletionDetector` is created, `lapProgress` is cleared, and both decimation states are cleared — exactly the state a brand-new session starts with. `sessionId` and `trackId` are preserved (same session, same track). A one-line log records the detected restart (packet count/session, Portuguese per convention). The threshold is a named, documented constant, following the same pattern as `MIN_DISTANCE_DELTA_M`/`MAX_TIME_GAP_MS` in `decimation.ts`.

**Why 100 is a safe threshold** (measured directly against the example recording, restricted to the four packet types that actually reach `getActiveSession` — packetId 0/1/2/6; a general UDP/event packet, id 4, showed an 80-frame dip in the raw file, but that packet type is never routed to `getActiveSession` at all, so it's irrelevant to this check):
- Largest backward step observed *within* a single pass, among packets that reach this check: **0**.
- Backward step at an actual loop restart (last pass-1 packet → first pass-2 packet): **4,476** frames (recording spans overall frame IDs 9,635 → 14,111 over 222,839 ms).
- 100 sits comfortably between both: far above any plausible reordering noise (observed: none) and far below a real restart (~45× smaller).
- A flashback (per the project's own documentation: `frameIdentifier` and `sessionTime` go backward, `overallFrameIdentifier` does not) cannot trigger this check by construction, since the check only ever looks at `overallFrameIdentifier`. This is locked in by an explicit unit test (see Testing, point 3) rather than left as an inference.

**Guaranteeing the integration test's synthetic recording actually exercises this path**: a synthetic recording whose `overallFrameIdentifier` span is below the 100-frame threshold would loop without ever triggering the reset, silently testing nothing about point 2 while still passing (the stale state wouldn't produce extra samples within such a short, hand-built fixture either, so the assertions would pass for the wrong reason). To rule this out:
- The fixture is built with `overallFrameIdentifier` running from **1000 to 1160** (span **160**, 60% above the threshold with explicit margin — not a value chosen to just barely clear it), a handful of packets spread across that range, `timestampMs` spaced a few milliseconds apart so even a `"1x"` pass finishes in well under a second.
- The test itself asserts `last.overallFrameIdentifier - first.overallFrameIdentifier > PASS_RESTART_THRESHOLD_FRAMES` on its own fixture **before** asserting anything about loop behaviour — a guard, not just a comment, so a future edit that shrinks the fixture fails loudly (wrong test, caught immediately) instead of silently exercising nothing.
- `PASS_RESTART_THRESHOLD_FRAMES` is exported from `sessionContext.ts` precisely so this guard (and the "small regression doesn't reset" unit test) can reference the real constant instead of a second, possibly-drifting copy of `100`.

**Known limitation (new, introduced by this feature)**: a *real* recording whose own `overallFrameIdentifier` span is **at or below the 100-frame threshold** will not trigger the pass-restart reset when looped — lap completion and decimation state will carry over stale from the end of the previous pass, reproducing the exact bug this feature fixes for longer recordings. This is inherent to a fixed-threshold heuristic and is accepted, not fixed, by this plan: the Interlagos example recording spans 4,476 frames (≈45× the threshold), and a recording that short in the first place (under a few seconds at the game's frame rate) is not a realistic demo or development fixture. A future improvement, if ever needed, would scale the threshold to a fraction of the recording's own span instead of a fixed constant — out of scope here. This limitation is recorded in README.md/CLAUDE.md alongside the other replay limitations (research.md point 5) as a task for `/speckit-tasks`.

**Alternatives considered** (presented to and chosen by the user over the alternatives):
- Resetting on *any* backward step, no threshold — rejected: would also fire on an ordinary UDP reordering during a real, live (non-replay) session, discarding in-progress decimation state and reprocessing a lap unnecessarily — a regression on today's live behaviour.
- An explicit out-of-band "pass boundary" signal sent by the replay tool itself — rejected: introduces a wire concept outside the F1 24 protocol the server has to recognise, coupling the server to the existence of a replay tool and enlarging the touched surface (`udpListener`, `dispatcher`) for a problem the existing header fields already solve.

## 3. Pure pacing function and clock injection (point 3)

**Decision**: a new `src/replay/` module, parallel to `telemetry/`, `persistence/`, `analysis/`, `coaching/`:
- `src/replay/types.ts` — `ReplaySpeed = "1x" | "2x" | "max"`, `ReplayOptions { speed: ReplaySpeed; loop: boolean }`, `RecordedPacket { timestampMs: number; data: Buffer }`.
- `src/replay/scheduler.ts` — **pure**, no I/O, no timers: `computeDelayMs(targetOffsetMs: number, elapsedMsSincePassStart: number, speed: ReplaySpeed): number`. `speed: "max"` always returns `0`. This is the unit-testable core: given a target offset, how long to wait, for each speed, is a one-line arithmetic fact and needs no clock at all to test.
- `src/replay/runner.ts` — the orchestration loop, `runReplay(packets, options, io)`, where `io` is injected and defaults to real implementations: `{ send: (buf: Buffer) => void; now?: () => number; wait?: (ms: number, signal?: AbortSignal) => Promise<void>; onPass?: (passNumber: number) => void }`. `now` defaults to `Date.now`; `wait` defaults to `node:timers/promises`' `setTimeout` (which natively supports `AbortSignal`, satisfying FR-009's "shut down cleanly mid-wait"). Each packet's send time is computed as an **absolute deadline** (`passStartTime + offsetMs/speedMultiplier`) rather than chaining relative waits, so scheduling error does not accumulate over a long recording (FR-004) — a well-known pattern for this exact failure mode.
- `tools/replayer.ts` becomes a thin CLI: argument parsing, reading the `.jsonl` file into `RecordedPacket[]` upfront (skipping and logging unparsable lines per FR-008), validating before sending anything (FR-007), creating the real UDP socket, wiring `SIGINT`/`SIGTERM` to an `AbortController` passed through as `io.wait`'s signal, and printing the start/end reports (FR-006).

**Clock injection for tests**: unit tests of `computeDelayMs` need no clock — it's pure arithmetic. Tests of `runReplay`'s *behaviour* (pass counting, loop restart, abort mid-wait) inject a fake `now`/`wait` pair (a manually-advanced counter and an immediately-resolving `wait` that records what it was asked to wait) so the full scheduling behaviour — including the FR-004 bound — is asserted deterministically in milliseconds of real test time, not minutes.

**Alternatives considered**: keeping all logic inside `tools/replayer.ts` — rejected outright, because `tools/` is outside `tsconfig.json`'s `rootDir` (`./src`) and outside every glob in `npm test`'s script; nothing there can be type-checked by `tsc --noEmit` or unit-tested by the existing test command without changing both, and the project's own convention already requires new pure logic to live in `src/`.

## 4. Integration test infrastructure (point 4)

**Decision**:
- **Database**: `src/config/env.ts` reads an optional `DB_PATH` environment variable; `src/persistence/db.ts` opens that path if set and non-empty, falling back to the existing fixed `data/telemetry.db` otherwise. An empty string is treated as "not set" (SQLite opens a private temporary database for an empty filename, which would silently defeat the whole point and give a confusing non-error). `db.ts` logs the resolved path once at module load (Portuguese, matching convention), so the override is visible, not silent. Production behaviour is unchanged: nothing sets `DB_PATH`, `.env.example` gains no new required variable, and the database path is "fixed by default; overridable only by the integration test," which is the phrase CLAUDE.md gets updated to.
- **Guaranteeing `DB_PATH` is set before `db.ts` opens the database**: TypeScript/ESM `import` declarations are hoisted to the top of a module's compiled output and executed before any other statement in that file — so a test file cannot `process.env.DB_PATH = ...` and then `import` a module that transitively opens the database; the import's `require` will already have run. The integration test file therefore sets `process.env.DB_PATH` as its first statement, then loads every module that touches `db.ts` (directly or transitively — `persistTelemetry`, the repositories, `sessionContext`) via a function-call `require(...)` (not a static `import`), which is **not** hoisted. This is the standard, minimal workaround for this specific Node/TypeScript ordering rule and needs no process-spawning. Node's test runner already isolates each test *file* in its own process, so this doesn't risk leaking `DB_PATH` into any other `*.test.ts` file's run.
- **Database file**: a uniquely-named temporary file under `fs.mkdtempSync(path.join(os.tmpdir(), "telemetryf1-replay-test-"))`, not `:memory:` (per the user's explicit choice — a real disposable file, not an in-process database). Removed in a `node:test` `after()` hook using `fs.rmSync(dir, { recursive: true, force: true })`, which runs whether the test passed or failed.
- **Port**: `startUdpListener(0, handler)` — Node's `dgram` already treats port `0` as "let the OS pick," and the function already returns the live `dgram.Socket`, so the test reads the real port back from `socket.address().port` with no code change needed in `udpListener.ts`.
- **Scope**: the integration test drives `startUdpListener` + the existing dispatcher + `persistTelemetry` directly, and calls `runReplay` (from point 3) against a tiny synthetic in-memory packet array built in the test itself (not a file on disk) — not through `tools/replayer.ts`'s CLI layer. It does **not** start the HTTP or WebSocket servers, since FR-013(b) only needs lap and sample counts, which are read directly from the repository functions / the temp database. This keeps the test to one ephemeral resource (the UDP port) and finishes in well under a second even at `"1x"` speed, since the synthetic recording's own offsets are a handful of milliseconds apart. Its `overallFrameIdentifier` values run 1000→1160 (span 160, with a self-asserting guard against `PASS_RESTART_THRESHOLD_FRAMES`) specifically so the loop-pass assertion exercises the point 2 reset rather than passing without ever triggering it — see point 2's "Guaranteeing the integration test's synthetic recording actually exercises this path."
- **`npm test` wiring**: add `src/replay/*.test.ts` to the script's glob in `package.json`, alongside the existing three folders. The integration test lives at `src/replay/replayIntegration.test.ts`; the pure scheduler tests at `src/replay/scheduler.test.ts`; the `sessionContext` pass-restart tests stay in `src/persistence/sessionContext.test.ts` (new file in an existing, already-covered folder).

**Alternatives considered**:
- `:memory:` — considered and initially proposed, but the user explicitly asked for a real temporary file with guaranteed cleanup, which also exercises the same on-disk code path (`fs.mkdirSync`, WAL mode) that production uses, rather than SQLite's separate in-memory engine.
- Swapping the real `data/telemetry.db` aside before the test and restoring it afterward — rejected: a crash mid-test before the restore step could destroy a developer's actual recorded session history; this is explicitly the kind of destructive, hard-to-reverse action this project's working agreement requires avoiding.
- Full dependency injection of the database connection through every repository — out of scope for this feature; recorded here as a future improvement if the project ever needs more than one isolated database per process (e.g., parallel test workers). The narrow override is proportionate to what this feature actually needs.
  - **Reinforced during implementation**: three separate tasks (the two repository tests and the integration test) each independently needed the same `DB_PATH`-plus-`require()` dance to avoid opening the real `data/telemetry.db`, and none of their original task descriptions said so explicitly — a real gap, not just a style preference. `src/persistence/testDb.ts` (tasks.md T005) centralises it: it sets `DB_PATH`, opens `./db`, and asserts the connection's `.name` matches the temp path before returning control, so a future test that gets this wrong fails immediately instead of silently writing into real data. That a *shared, asserting* helper was worth building — rather than three independent copies — is itself evidence for the full-DI alternative above: the moment a fourth caller needs the same isolation, the asserting-`require()` pattern is worth replacing with real dependency injection instead of extending further.
  - Confirmed empirically (not assumed) that this is safe: `node --test fileA.test.ts fileB.test.ts` runs each file in its own process, so one file's module cache (and its `DB_PATH`-opened `db` singleton) cannot leak into another's.

## 6. Baseline measurement: real sample loss on the published recording (new, requested before `/speckit-tasks`)

**Why**: the numbers this plan would otherwise have quoted in README.md/CLAUDE.md (point 5) were exactly the kind of untraceable figure that got removed from `main` — measured once, on a different recording, never re-verified against the file actually published. This plan does not repeat that mistake: it measures the real loss on `demo-interlagos-tt-20hz-laps6-8.jsonl` twice — once **before** any implementation code changes (the baseline, today's unpaced-only behaviour), once **after** (with `--speed=1x`) — and only those two measured numbers go into the docs.

**Decision — how "samples that should exist" is computed**: not by eye, and not by running the lossy UDP path twice. The recording's packets are fed, in-process, through the **real, unmodified** `src/telemetry/dispatcher` + `persistTelemetry` + `sessionContext` — i.e., calling the actual parsing and decimation code directly as function calls, with no `dgram` socket involved at all — against a disposable database (the `DB_PATH` override from point 4, reused here for exactly the purpose it was built for). Since there is no network layer in this path, nothing can be dropped for lack of receive capacity; the resulting sample count is the ground truth for "how many samples this recording should produce," independent of anything this feature changes.

**Decision — how "samples actually delivered today" is measured (the baseline)**:
1. **Back up** `data/telemetry.db` and its WAL/SHM sidecars if they exist (`data/telemetry.db-wal`, `data/telemetry.db-shm`) — e.g. copy each to a `.baseline-backup` suffix. If `data/telemetry.db` doesn't exist yet, record that fact (so "restore" means "delete the file this measurement created," not "overwrite with a backup that was never taken").
2. Run `npm run dev` and, in the **current, unmodified** `tools/replayer.ts` (before any of this feature's code lands), `npm run replay -- recordings/demo-interlagos-tt-20hz-laps6-8.jsonl` — today's only mode, unpaced, over the real UDP socket.
3. After the replayer reports it has sent every packet, wait briefly for the server to finish processing its receive buffer, then count `car_telemetry_samples`/`motion_samples` rows for that session.
4. **Restore**: stop `npm run dev`, delete the database the measurement just created, and move the backed-up files back (or confirm no file existed before, per step 1).
5. Baseline percentage = (rows counted in step 3) ÷ (ground-truth count from the in-process run above).

**Decision — the same measurement, repeated after the fix**: identical procedure, except step 2 uses the finished `--speed=1x` replay instead of today's unpaced one, and SC-001's "at least 99%" is checked against this second percentage, not assumed.

**Where this lives**: as explicit, ordered tasks in `tasks.md` — the baseline (steps 1–5 above) scheduled **before** any implementation task touches `src/`, the backup/restore wrapping it so a crash mid-measurement can't leave `data/telemetry.db` corrupted or swapped, and the post-fix repeat scheduled **after** the replay/schema/sessionContext work, immediately before the README/CLAUDE.md docs task from point 5. This plan does not run the measurement itself — `/speckit-tasks` turns it into tasks the implementation phase executes in that order.

**Alternatives considered**:
- Trusting the spec's own illustrative "21–33%"/"67–79%" figures (inherited from the user's original framing, itself referencing the old README's now-removed numbers) — rejected for the docs: they describe the *old, different* test recording the previous numbers came from, which is exactly the provenance problem `52b3b21` just fixed. They remain fine as spec-level motivating context (`spec.md` is unchanged by this plan revision), but nothing republished to README/CLAUDE.md repeats them as if they were measured against this file.
- Measuring "ground truth" by running the fixed `--speed=max` mode over real UDP instead of in-process — rejected: `max` is the same unpaced path being measured as lossy; it cannot serve as its own denominator.
